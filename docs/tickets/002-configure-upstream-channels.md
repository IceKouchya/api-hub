# 002：配置上游渠道与模型映射

- **状态：** `ready-for-agent`
- **依赖：** 001 部署 New API 基线完成并通过持久化验证
- **后续解锁：** 003 创建统一 Token
- **执行角色：** 独立配置窗口；真实凭据由修本人在后台输入

## 目标

将修合法持有或获得授权的上游服务逐个登记为 New API 渠道，建立统一模型名、真实模型 ID、能力、优先级和备用关系的可验证映射。完成后至少一个渠道可通过后台或受控测试成功响应；客户端仍不保存上游 API Key。

## 允许修改范围

- 已部署 New API 的管理后台渠道、模型映射和渠道状态配置。
- `D:\Agent-Codex\projects\api-hub\` 中由 001 建立的受控运行资料，但不得将真实凭据写入可追踪文件。
- 本项目 Vault 中的脱敏渠道清单、验证记录与票据状态。

## 禁止修改范围

- 客户端应用、IDE 或脚本中的上游密钥配置。
- Workbench、其他项目、无关 Docker 容器和网络设置。
- 未经修授权的上游、未知来源中转服务或绕过服务条款的接口。
- 公网访问、公开注册、支付或 Token 对外分发。
- 将 API Key、完整 Base URL 敏感参数、Cookie、Token 或完整错误日志粘贴进 Vault、Git 或聊天。

## 配置前的渠道清单

在录入前，为每个上游建立一行脱敏清单，至少包括：

| 字段 | 说明 |
| --- | --- |
| 渠道代号 | 如 `provider-a-primary`，不得把凭据写进名称 |
| 授权状态 | 确认由修合法持有或获得授权 |
| 协议类型 | OpenAI 兼容或 New API 当前版本支持的其他内置类型 |
| Base URL | 仅在后台录入；文档中只保留域名或脱敏说明 |
| 真实模型 ID | 以实际模型发现或文档核实为准 |
| 支持能力 | 普通对话、流式、工具、视觉、推理、嵌入等，未知则标未知 |
| 统一模型名 | 如 `chat-general` |
| 角色 | 主渠道、备用渠道或仅专项渠道 |
| 优先级/权重 | 明确数值及其原因 |
| 验证结果 | 成功、失败类别、时间和后续动作 |

## 实施步骤

1. 从一个最简单、最确定的 OpenAI 兼容上游开始。不要一口气批量录入所有渠道；先让一条路径真正跑通，省得日后面对一墙绿色配置却没有一个能说话的模型。
2. 在 New API 后台创建渠道，选择与目标上游实际协议一致的渠道类型。
3. 由修本人通过后台安全输入上游 API Key；执行窗口不得要求将 Key 发送到聊天、写入 Markdown 或保存为未受控文本。
4. 录入 Base URL、真实模型 ID 和必要配置；仅使用上游文档已确认的参数，避免猜测性覆盖。
5. 为该渠道与模型建立能力档案，覆盖普通对话、流式、工具调用、流式工具调用、视觉输入、推理控制、Embedding 与实际原生协议入口；未知项先标记为未验证，不凭模型宣传推断为已通过。
6. 为通过验证的能力创建统一模型名或明确端点映射。`chat-general`、`chat-fast`、`reasoning`、`vision` 与 `embedding` 都属于第一阶段路线；Embedding 必须走独立 `/v1/embeddings` 路径并记录向量空间。
7. 按 [能力矩阵](../API-CAPABILITY-MATRIX.md) 进行单渠道验证：
   - 模型发现或等效验证，以及非流式文本对话。
   - 流式文本响应完整结束。
   - `tools`、`tool_choice` 和 `tool_calls`；支持流式工具调用时，还要验证增量参数可以完整组装。
   - 图片内容块与可验证图片理解结果。
   - `reasoning_effort` 或该协议的等效推理控制。
   - `/v1/embeddings` 返回非空向量，并记录模型、维度、批量与编码格式。
   - Claude、Gemini 或其他原生/转换协议路径分别测试；文本能通不等于工具或视觉能通。
8. 为同一公开路由建立备用渠道前，确认两个渠道的能力契约兼容。工具 schema、图像格式、推理控制、流式行为、上下文限制与向量空间不一致时，不建立该能力的备用关系。
9. 配置主/备用优先级和权重。对于首批路径，先使用简单、可解释的“主高、备低”优先级，不需要为了看起来高级而做多层随机策略。
10. 受控验证：在不删除配置的前提下暂时禁用主渠道，确认可重试故障时能力兼容备用渠道被选择；恢复主渠道后复测。
11. 记录脱敏后的渠道清单、能力矩阵和验证结果；不要保存请求中的认证头、完整原始响应或上游账单信息。

## 路由规则

- 优先使用支持目标统一模型名、处于启用状态且优先级最高的渠道。
- 同优先级渠道使用权重前，必须有明确用途，例如成本或地域分散；否则只保留一个主渠道。
- 只对网络超时、暂时不可用、`429` 或经文档确认的部分 `5xx` 使用有限重试或备用切换。
- `400`、`401`、`403`、模型不存在、请求超出模型能力和参数错误应直接暴露，供修正渠道配置。
- 流式内容一旦已向客户端输出，不重放完整请求。
- 涉及工具调用的请求必须额外考虑副作用和重复计费风险；工具调用通过验证后仍不在已开始执行或已输出流式内容的请求上自动完整重放。
- Embedding 备用渠道必须使用同一向量空间；不同嵌入模型不得相互接管。

## 验收标准

1. 每个启用渠道都有渠道代号、协议、真实模型 ID、统一别名、完整能力矩阵与验证记录。
2. 每个首批公开路由均完成其声明能力的测试：文本、流式、工具、视觉、推理或 Embedding；未支持项明确标记。
3. 上游 API Key 只保留在 New API 受控渠道配置中。
4. 所有公开给客户端的模型名均为已验证能力，不直接暴露供应商耦合的真实模型 ID。
5. 主/备用关系明确，且备用渠道只用于能力契约匹配的路径；不同向量空间不做 Embedding 备用。
6. 主渠道受控不可用时，确认的备用渠道可以在可重试类别下接管。
7. 配置错误不会被无限重试掩盖。

## 失败处理与回滚

- 单一渠道失败：禁用该渠道或移除未完成配置，不影响已经通过验证的渠道。
- 模型映射错误：只修改对应映射，重新进行该路径测试。
- 备用渠道能力不等价：解除备用关系，记录限制，不做伪兼容。
- 凭据疑似泄露：立即在上游撤销或轮换该 Key，再更新后台；文档只记录“已轮换”，不记录旧值。
- 不删除已验证主渠道以测试回退；应使用启停或优先级调整等可恢复方式。

## 完成报告

报告列出脱敏渠道代号、统一模型名、真实模型 ID、能力、主/备关系、测试类别、成功或失败结论以及下一步。不得包含真实 Key、认证头、敏感 URL 参数或完整日志。
