# ADR-0001：选择 New API 作为个人局域网 API Hub

- **状态：** 已确认，待实施
- **日期：** 2026-09-05
- **决策人：** 修
- **适用范围：** API Hub 第一阶段

## 背景

修需要将多个已授权的大模型上游服务统一为一个个人可控入口。客户端应只记住一个 OpenAI 兼容 Base URL、一个 New API Token 和稳定的能力导向模型别名；上游 API Key、真实模型 ID 与渠道选择逻辑应留在网关内部。

目标环境是修本人控制的 Windows 主机和受信任局域网设备。项目需要 Web 管理后台、渠道管理、模型映射、Token 管理、基本日志与故障切换，但不需要公共 API 平台、多租户运营或公网服务。

## 决策

第一阶段选择 **New API** 作为网关，采用 **SQLite 单容器** 部署形态，限制为 **仅局域网访问**。

运行时由 New API 对外提供统一 OpenAI 兼容 `/v1` 入口；客户端只保存 New API Token；每个上游服务以渠道形式在管理后台配置；统一模型名通过渠道映射转为上游真实模型 ID；主/备用渠道仅对被定义为可重试的故障进行有限故障切换。

## 备选方案

### LiteLLM

LiteLLM 是更偏工程化的 LLM Gateway，支持模型别名、路由、回退、OpenAI 兼容接口与管理能力。

未选择的原因：对于当前“个人内网、希望在可视化后台直接管理渠道、Token、模型和用量”的目标，New API 的产品表面更贴近需要。LiteLLM 并非不可用，而是在本阶段会引入更偏工程配置与数据库管理的复杂度，收益不明显。

### 从零编写反向代理

未选择的原因：将自行承担 OpenAI 兼容细节、流式响应、认证、上游差异、日志、重试、故障切换、安全更新与管理后台开发。这会把“集中已有服务”的问题变成维护新的网关产品，明显偏离目标。

### New API + PostgreSQL + Redis

未选择为第一阶段的原因：该组合适合更高并发、更强长期扩展或多实例需求，但当前个人局域网使用规模不需要先承担额外容器、凭据、维护与迁移成本。

保留条件：当 SQLite 出现明确并发、日志、稳定性或维护瓶颈时，新建迁移 ADR 与执行票后再升级，不能临时在现有部署上拼装组件。

### 公网暴露或私有组网

未选择为第一阶段的原因：当前需求是受信任局域网设备调用。公网暴露显著扩大攻击面；私有组网属于有价值但未确认的后续需求。二者均不应在没有独立安全设计、访问策略和验收标准时提前启用。

## 后果

### 正向后果

- 客户端接入简化为一个 Base URL、一个 Token 和稳定模型别名。
- 上游 API Key 与客户端解耦，便于撤销、轮换和统一管理。
- 渠道、模型映射、优先级、权重和日志集中在一处。
- 单容器 SQLite 初期运维面较小，方便备份与回滚。
- 项目不修改 Workbench，也不需要自行开发网关。

### 约束与风险

- New API 的版本和安全公告必须持续审查，不能盲目使用 `latest`。
- SQLite 不适合被误用为大规模并发或生产多租户数据库。
- 工具调用、视觉输入、推理控制、流式输出与 Embedding 属于第一阶段能力矩阵；上游能力并不天然等价，统一模型名只能代表实际验证过的能力契约。
- 协议转换路径可能缩减能力；例如官方 README 标注的 Google Gemini 转 OpenAI Compatible 当前仅文本且不支持 function calling。
- 故障切换无法消除语义差异、流式中断或可能的重复计费风险。
- 局域网并不自动等于安全，仍需密码、Token、Windows 防火墙和受信任设备范围。

## 验收影响

本 ADR 的执行必须证明：

1. 至少一个统一模型名能通过统一 `/v1` 入口成功调用。
2. 客户端不保存上游 API Key。
3. 持久化配置可在容器重启后保存，并能从备份恢复。
4. 受控主渠道失效时，备用渠道仅按可重试策略接管。
5. 网关未被配置为公网、公开注册、支付或 API 转售服务。

## 复审触发条件

出现以下任一情形时复审本 ADR：

- 需要跨网络访问。
- 多设备并发或数据规模已成为 SQLite 的明确瓶颈。
- 目标上游大量不兼容 New API 的可用渠道类型。
- New API 的安全状况、许可或维护状态发生重大变化。
- 需要多租户、计费或公共服务能力。
