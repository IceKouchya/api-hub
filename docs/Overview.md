# API Hub 项目总览

## 项目背景

修需要将多个已授权的大模型上游服务集中到一个个人可控入口，避免在不同中转站、不同 Base URL 与不同调用密钥之间反复切换。

本项目创建独立的个人局域网 API Hub：由 New API 充当网关，对客户端提供统一 OpenAI 兼容入口、统一模型别名与统一 New API Token；网关在内部管理多个上游渠道、模型映射、优先级、必要的故障切换和日志。

本项目不属于 Workbench。Workbench 继续作为本地静态控制台；API Hub 是独立运行的网关项目。

## 当前阶段目标

建立可交给执行窗口的完整项目资料，使其能在不依赖聊天记录的情况下按已确认边界部署并验证个人局域网 API Hub。

第一阶段运行目标：

1. 在 Windows Docker Desktop 中运行固定版本的 New API。
2. 使用 SQLite 单容器，并挂载持久化 `/data` 与日志目录。
3. 仅允许受信任局域网设备通过 Windows 主机局域网 IP 访问。
4. 对客户端暴露统一 OpenAI 兼容 `/v1` 入口。
5. 客户端仅使用 New API Token；上游 API Key 仅保存于渠道配置。
6. 使用能力导向的统一模型名路由到不同上游真实模型 ID。
7. 支持经验证的主渠道、备用渠道及有限可重试故障切换。
8. 在部署、配置和升级前后具备备份、验证与回滚路径。

## 已确认范围

### 统一调用模型

客户端使用：

```text
Base URL: http://<Windows-LAN-IP>:3000/v1
Authorization: Bearer <NEW_API_TOKEN>
```

典型请求：

```http
POST /v1/chat/completions
Content-Type: application/json
Authorization: Bearer <NEW_API_TOKEN>
```

请求中的 `model` 使用统一模型名，例如 `chat-general`，而不是上游供应商的真实模型 ID。渠道负责完成映射和转发。

### 能力矩阵

工具调用、视觉输入、推理控制、流式输出与 Embedding 是第一阶段实施和验收范围。网关不对模型和渠道已经支持的能力做项目层禁用；实际是否向客户端开放，以“New API 接口与版本、渠道协议路径、上游模型和账户权限”同时通过真实验证为准。

- 工具调用、视觉输入和推理控制属于聊天或原生模型请求能力。
- Embedding 使用独立 `/v1/embeddings` 端点与嵌入模型，不能从聊天模型支持情况推导出来。
- 协议转换路径必须单独验证。New API 官方 README 已标注 Google Gemini 转 OpenAI Compatible 当前仅文本，暂不支持 function calling。
- 主/备用渠道必须满足相同能力契约；同一个模型名不足以证明工具、视觉、推理、流式或向量空间兼容。

具体的验证维度、通过条件与已知例外以 [API-CAPABILITY-MATRIX.md](API-CAPABILITY-MATRIX.md) 为准。

### 渠道与路由

每个上游服务在 New API 中作为独立渠道维护，至少记录：

- 渠道名称与服务类型。
- 脱敏后的上游用途说明。
- Base URL。
- 上游 API Key。
- 已验证的真实模型 ID 与能力。
- 统一模型名到真实模型 ID 的映射。
- 优先级、权重和备用关系。
- 连通性验证结果与最近变更时间。

路由原则：

1. 先依据统一模型名筛选可用渠道。
2. 优先级更高的渠道先被选择。
3. 同优先级渠道可按权重分配。
4. 只有超时、限流、暂时不可用或被确认的部分 `5xx` 才能进入重试或备用渠道。
5. `400`、`401`、`403`、模型不存在和参数不兼容必须保留为明确错误，不得用无限重试掩盖配置问题。
6. 流式响应已开始输出后，不自动完整重放到备用渠道。

### 部署形态

第一阶段采用 SQLite 单容器，而非 PostgreSQL + Redis：

- 面向修本人及少量自有设备的局域网使用。
- 优先降低组件数、运维成本和故障面。
- 使用固定镜像版本，不使用未审查的长期 `latest` 部署策略。
- `/data` 必须挂载到宿主机持久化目录；日志也应保留在项目目录中。
- PostgreSQL + Redis 是明确的后续扩展，不属于第一阶段交付。

### 安全边界

- 仅接入修合法持有或获得授权的上游账号、API Key 与模型服务。
- 不公开为 API 转售平台，不提供公开注册、支付、充值或社交登录。
- 不做路由器端口转发，不开放公网地址。
- Windows 防火墙只对受信任私有网络与所需局域网范围开放端口。
- 管理后台使用强管理员密码；客户端 Token 与上游 API Key 分离。
- 不将真实 API Key、Token、管理密码、完整备份或敏感日志写入 Git、Vault 文档、Canvas、截图或聊天交接。
- New API 存在历史安全公告；执行前必须复核目标固定版本的 release notes 与安全公告，关闭不需要的能力。

## 明确不做

- 不修改 `D:\Agent-Codex\projects\workbench\` 或其 Vault 文档。
- 不自行开发新的模型网关、反向代理或多协议适配器。

- 不把未通过渠道级验证的能力、协议转换或主备兼容性对客户端伪装为可用；已支持并通过验证的能力纳入第一阶段开放范围。
- 不写入真实上游 API Key、New API Token、管理员密码或敏感备份。
- 不在本文档阶段创建或启动 Docker 容器、拉取镜像、生成 Compose 运行配置。

## 成功标准

1. 执行窗口能仅依据本目录文档完成环境盘点、部署、配置、验证和交接。
2. 所有运行变更严格位于未来的 `D:\Agent-Codex\projects\api-hub\`，且不会触碰 Workbench。
3. 局域网客户端只需一个统一 Base URL 与一个 New API Token。
4. 每个首批公开路由按能力矩阵如实完成普通对话、流式、工具调用、视觉输入、推理控制或 Embedding 的验证；未支持项明确标记，不做项目层人为降级。
5. 主渠道受控不可用时，能力契约兼容的备用渠道能按规则接管；配置类错误不被伪装成可恢复。
6. 容器重启后持久化配置仍存在，且备份可按票据恢复并回归已启用能力。
7. 项目文件、日志和版本控制中不存在真实密钥或 Token。
8. 项目作为独立 Git 仓库维护，公开远程仓库经审查推送后可进入 TDAI CodeGraph 索引流程。
