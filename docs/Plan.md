## 部署方案与取舍

### 第一阶段：SQLite 单容器

选择理由：

- 当前使用者是修本人及少量自有设备。
- 局域网范围降低了网络暴露面。
- 单容器便于核对运行状态、数据目录和回滚版本。
- 组件更少，降低初期维护复杂度。

硬性要求：

- 镜像必须固定到经核对的明确版本或摘要。
- 运行数据必须映射到宿主机目录，不能依赖容器内部临时层。
- 升级前必须备份数据、记录当前镜像版本并验证回滚命令。
- 目标版本需再次阅读 release notes 与安全公告；历史最新版本不能自动替代当前审批。

### 后续扩展：PostgreSQL + Redis

只在以下情形重新评估：

- 多设备持续并发且 SQLite 成为明确瓶颈。
- 日志、统计或管理需求增长到单文件数据库无法稳定承载。
- 需要更完善的数据库维护、恢复和多实例能力。

触发后应新建 ADR 和迁移票，不得在现有单容器上临时拼接组件。

## 版本与安全核查清单

每次部署或升级前：

1. 查询目标 New API 版本、发布日期、release notes 与安全公告。
2. 确认镜像仓库、标签或摘要与该版本匹配。
3. 检查上游 API Key、Token 和管理员密码不出现在命令历史、文件内容或截图中。
4. 检查 Docker 端口、Windows 防火墙规则和局域网地址变化。
5. 备份当前 `/data`、记录当前镜像与容器状态。
6. 在升级前明确通过条件和恢复条件。

## 统一模型命名策略

默认只创建经验证的别名：

| 别名 | 目标能力 | 首次验证要求 |
| --- | --- | --- |
| `chat-general` | 通用文本对话 | 非流式对话成功 |
| `chat-fast` | 低延迟或低成本对话 | 明确性能/成本取舍且对话成功 |
| `reasoning` | 推理任务 | 上游对应能力和参数行为经验证 |
| `vision` | 图像输入 | 图像格式与响应行为经验证 |
| `embedding` | 向量化 | 独立 `/v1/embeddings` 路径、模型、维度与向量空间验证 |

工具调用、视觉输入、推理控制、流式输出与 Embedding 均属于第一阶段能力矩阵：渠道和模型支持时不做项目层禁用；未核实或未通过的能力必须如实标为待验证或不支持，不能作为已验证公开路由或能力兼容备用链。每个渠道的真实模型 ID、上下文限制、流式支持、工具调用支持和已知限制必须记录在执行票或渠道清单中。

## 验收门槛

### 部署基线

- 项目运行目录在 `D:\Agent-Codex\projects\api-hub\`。
- New API 后台在本机可访问。
- Docker 重启或容器重启后，数据库和基本设置保持存在。
- 没有修改 Workbench 或其他项目。

### 渠道和 Token

- 上游 Key 不离开管理后台或受控运行配置。
- 客户端使用 New API Token，不使用上游 Key。
- 至少一个渠道以统一模型名完成成功调用。
- 对不可用渠道有明确错误与日志，不把失败伪装为成功。

### 局域网与故障切换

- 受信任局域网客户端能以统一入口调用。
- 不在公网、访客网络或未经授权设备上开放服务。
- 主渠道被受控禁用时，备用渠道仅在可重试故障下接管。
- `400`、`401`、`403`、模型不存在和不兼容参数不做无限重试。
- 已启动的流式响应不自动完整重放。

### 备份与回滚

- 已有可定位的持久化备份、镜像版本记录和恢复步骤。
- 已完成至少一次不含真实密钥暴露的恢复演练。
- 升级失败时能回到已验证版本，且以功能调用验证恢复成功。
